## 3. Findings from the limits check

Recorded by the two agents; no code, Terraform or configuration was changed (Terraform is frozen in Phase 17, and step L was read-only). Each is a candidate for the "proposed later" list unless the human routes it.

| ID | Source | Finding |
|---|---|---|
| I-1 | step I1a, RISKS (1); IL-11 | The documented default Fargate On-Demand vCPU quota is 6 per Region. At the deployed maximums the four services need 6 vCPU and one ops task 1 more (7 vCPU, estimate), so full scale with an ops task exceeds the documented default. The course account's applied quota was not checked. |
| I-2 | step I1a, RISKS (2); IL-08 | Fargate ARM64 is not supported in the us-east-1 AZ ID `use1-az3`. The network module picks the first two AZ names (`infra/terraform/modules/network/main.tf:22`) and does not exclude that AZ ID. Phase 14 and 15 tasks ran, so it did not block the course run; it is a limitation for a new account. |
| S-1 | step L, R1; SL-12, SL-13 | `vectors.queryTopK` is validated only as `> 0` (`core/config/ConfigLoader.scala:712`), and `S3VectorsIndex.query` reads only the first response page (`storage/aws/S3VectorsIndex.scala:144`, no `nextToken`). QueryVectors returns at most 100 results per page, so a configured top-K above 100 would return at most 100. **The adapter does not support a top-K above 100.** Today's value is 30 (`config/course.json:58`), so there is no effect now. |
| S-2 | step L, R2; SL-23 | **No server-side Neptune query timeout of 20 s was configured.** The 20 s is the client's budget (SDK `apiCallTimeout`, `storage/aws/NeptuneAdapters.scala:273`). Terraform does not set `neptune_query_timeout` (`infra/terraform/modules/neptune/main.tf:27-54`), so Neptune's default of 120,000 ms applied, and a query the client abandoned could keep running on the server for up to 120 s. |
| S-3 | step L, R3; SL-30 | **Neptune bulk loads are not all-or-nothing.** With `failOnError` TRUE a bad row stops the load, and the data loaded up to that point persists (loader page). The code comment at `storage/neptune/BulkLoadRequests.scala:10` ("instead of loading a partial graph") says otherwise; the behaviour is unchanged, only the comment is inaccurate. |
| S-4 | step L, R4; SL-07 | Which index mode the removed vector indexes had is not established. The code enforces the stricter CLASSIC limits, which lie within both modes. |
| S-5 | step L, R5; SL-15 | The S3 Vectors write-rate limits are declared (`storage/StorageLimits.scala:32-33`) but not enforced; ingest relies on retry with backoff on throttling. |
| S-6 | step L, R6; SL-39 | With `maxReceiveCount` 5 on a standard queue, SQS moves a message received 3 or more times without deletion to the back of the queue (documented). Harmless for the job flow, whose attempts are bounded at 3 by the worker. The Phase 15 experiment F record shows the poison message reaching the dead-letter queue after 5 receives ([`docs/incidents/INC-P15-F-poison-message.md`](incidents/INC-P15-F-poison-message.md)). |
| S-7 | step L, R7; SL-14 | A filtered vector query can return fewer than top-K results (documented, either mode); callers already treat result counts as "at most". |
