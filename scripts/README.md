# ScholarChain scripts: reproduction guide

Owner: infra-engineer. This file is the reproduction guide until the root `README.md` links to it (documentation-engineer, Phase 17; planned deviation 12.5). The scripts are the only interface: there are no GitHub Actions (planned deviation 12.4). Each script's `--help` text is its full contract; this page summarizes them and gives the order of a full reproduction.

Status of every script: `static: shellcheck clean`, `human execution required`. No agent runs any script. Runtime (Phase 15 L-06: the earlier blanket "runtime: untested" was stale): the human ran check.sh, package.sh, plan.sh and `archive-evidence.sh --local-only` in Phase 13; check.sh, package.sh (also `--publish`), plan.sh, deploy.sh, smoke-test.sh, run-bounded-pipeline.sh and archive-evidence.sh (S3 mode) in Phase 14; plan.sh, deploy.sh, smoke-test.sh, run-bounded-pipeline.sh, run-experiment.sh, archive-evidence.sh and cleanup.sh in Phase 15; check.sh and the emulator scripts (env.sh, setup.sh, probes.sh) in Phase 16. Each run, its exit code and its record are in that phase's `docs/agent-runs/phase-NN/runbook-log.md` (Phase 13: its human gate); a failed attempt there stays a failed attempt. rollback.sh has never run (`runtime: untested`). Each script's own header holds its current runtime line: a part changed after its last run is `runtime: untested` until the human runs it again; Phase 17 changes (release-manifest.sh, the env.sh `SCHOLARCHAIN_CFG_*` sweep, probes.sh P16-B-03, deploy.sh help text E-01, archive-evidence.sh E-03) are `runtime: untested`.

## The two identity rules (scripts/lib/identity.sh)

- Build commit: `git log -1 --format=%H -- build.sbt project modules prompts docker config .scalafmt.conf .jvmopts .sbtopts`. Image tags, artifact keys (`artifacts/BUILD_COMMIT/`) and the `--code-version` of every job use it. Commits that change only scripts, Terraform, tests or evidence keep it.
- Plan validity: plan.sh names a plan `PLAN_COMMIT-PLAN_ID.tfplan`. deploy.sh and `cleanup.sh --remove` find the plan by its sha256 and use it only on a clean tree, with `PLAN_COMMIT` equal to HEAD or an ancestor, and with no plan input changed since. The plan inputs are `SC_PLAN_INPUT_PATHS` in `scripts/lib/identity.sh`: `infra/terraform/` plus every repository file outside it that Terraform reads (`file()`, `templatefile()`, `filebase64()` and similar), today `modules/storage/src/main/resources/s3vectors/index-spec-v1.json` (read by `infra/terraform/environments/course/main.tf`); a new such read must be added to that list. The approval is a committed whole line `APPROVED-PLAN-SHA256: HEX64` in a `human-gate.md` or `approvals.md` under `docs/agent-runs/`.
- Dirty trees: package.sh, plan.sh (for a usable plan), deploy.sh, cleanup.sh, run-bounded-pipeline.sh and run-experiment.sh refuse a dirty tree; check.sh, smoke-test.sh and archive-evidence.sh record the dirty flag; rollback.sh keeps its Phase 12 rule.

## check.sh gate 4 (shellcheck) scope

Gate 4 runs `shellcheck -x -P SCRIPTDIR` on `scripts/*.sh`, `scripts/lib/*.sh`, `datasets/scripts/*.sh` and `infra/terraform/modules/emr/files/bootstrap.sh` only. The hooks and hook self-tests under `.claude/**` (owned by factory-engineer) are not shellchecked here; they are covered by gate 1 (`.claude/hooks/validate-agent-files.sh`) and gate 3 (`bash -n` on every hook and self-test, then both self-tests). The full gate list is in `scripts/check.sh --help`.

## Release manifest (Phase 17, decision 7 item 1)

`scripts/release-manifest.sh` is an eleventh script, outside the table above. Status: `static: shellcheck clean`, `runtime: untested` (until the human's E10 run, Phase 17 decision 18), `human execution required`.

| Command line | Reads | Environment variables (names) | Human approval points | Writes | Cloud | Rollback behavior |
|---|---|---|---|---|---|---|
| `bash scripts/release-manifest.sh --clone PATH --marker PATH --out-dir PATH` | this working tree at HEAD (`git ls-tree`, `git cat-file`, `git grep` of the committed `APPROVED-PLAN-SHA256:`, `APPROVED-MANIFEST-SHA256:` and `EVIDENCE-ARCHIVE-SHA256:` lines in `docs/agent-runs/**/approvals.md` and `human-gate.md`), `releases/course/*.json`, `datasets/dataset-manifest.yaml`, `config/course.json`, `prompts/**`, `experiments/raw/`, `experiments/evaluation/raw/`, `experiments/emulator/raw/`; the four jars in the clone; the `--marker` file | `TMPDIR` (private temporary folder) | the human runs it at E10 (dry run at E5 with an `--out-dir` under `/tmp`) and commits `releases/manifest/RC_SHA/` | `OUT_DIR/RC_SHA/release-manifest.json` and `release-manifest.md` (RC_SHA = full HEAD SHA), through `OUT_DIR/.incomplete-RC_SHA-XXXXXX/`; inside this repository only `--out-dir releases/manifest` is accepted | none (no network, no AWS, no Terraform, no sbt) | nothing to undo: a folder is never overwritten; a repeated E10 at a new HEAD writes a new folder |

- **Options:** `--clone` is the top folder of the fresh clone of E3 (not this tree), whose HEAD must equal this tree's HEAD; it is used only to hash the jars. `--marker` is the saved copy of the clone's `.claude/.last-test-run` taken right after E3 (`timestamp=`, `module_tests=`, `contract_tests=` lines). `--out-dir` receives `RC_SHA/` and is created if missing (its parent must exist).
- **Order of checks, each refusal writes nothing:** options (2); repository root (4); tools `git jq unzip` and `shasum` or `sha256sum` (3); `--marker` exists (3); `--clone` is the top folder of a Git working tree (3) and not this tree (4); clone HEAD equals this HEAD (3); exactly one of each mandatory jar in the clone (3 when missing, 6 when more than one); this tree is clean (4); `--out-dir` accepted and `RC_SHA/` absent (4). The jar checks come before the clean-tree check, so `check.sh`'s probes give their stated codes on a dirty tree too.
- **Mandatory jars:** the four jars `project/PackageCheck.scala` opens, at the paths `scripts/package.sh` (`check_jars`) uses: `modules/hadoop/target/scala-*/scholarchain-hadoop-assembly-*.jar`, `modules/entity-resolution/target/scala-*/scholarchain-entity-resolution-assembly-*.jar`, `modules/spark/target/scala-*/scholarchain-spark-analytics-assembly-*.jar`, `modules/services/target/scala-*/scholarchain-services-assembly-*.jar`. None is optional. `check.sh` gate 7 builds all four (`sbt -batch packageCheck` depends on the four assemblies). If one is missing in the clone, build it there with `sbt -batch packageCheck` (all four), or `sbt -batch packageJobs` (hadoop, entity-resolution, spark) plus `sbt -batch services/assembly`. A jar whose `scholarchain-build-info.properties` has a `buildCommit` other than the build commit, a `module` other than expected, or `buildDirty` other than `false` is refused (6). `package.sh` runs `sbt clean` and rebuilds the jars, so run it (E5) before E10, never between E10 and E11's checksum recomputation.
- **Contents, each with its source path:** release candidate and build commit; planned tag `v1.0-submission`; per release record its commit, plan commit, plan sha256, environment, Region, image repository, tag and digest, per service the task definition, previous task definition, image tag and digest check, and whether a committed `APPROVED-PLAN-SHA256:` line carries the same sha256 (file and line); every signed plan checksum with its file and line; every signed experiment manifest; the dataset snapshots and checksums (with their line in `datasets/dataset-manifest.yaml`); run IDs (the Spark graph runs named in `experiments/raw/*/*/run-record.json`, every experiment attempt folder, every evaluation run folder, every emulator run folder, all from `git ls-tree HEAD`; local-only evidence archives as `local only` with their committed checksum line); every file under `prompts/` with its sha256; the model identifiers from `config/course.json` with their field paths; the test counts from `--marker`, labelled E3 with the tested SHA; sha256, size and build info of the four jars; the sha256 of key committed artifacts at HEAD (the dataset manifest, `config/course.json`, `project/PackageCheck.scala`, the signed experiment manifests, `experiments/evaluation/suite-v1.json`, `evaluate.py`, every `frozen-files-sha256-E12.txt`, every tracked `*.sha256` under `docs/agent-runs/` and `experiments/`, the release records, the approval files that hold an `EVIDENCE-ARCHIVE-SHA256:` line); and the rule line for commits after the release candidate (Phase 17 decision 7 item 1, applied at E12). Repository files are hashed as committed at HEAD (`git cat-file`), equal to `shasum -a 256` of the file on a clean checkout.
- **Identifier check (exit 8), before anything is written to `OUT_DIR`, and again on the written files:** a twelve-digit number (an alphanumeric token of exactly 12 digits) other than the placeholders `123456789012` and `210987654321` and a 12-character prefix of a commit of this repository (for example the release record name `20261119T193246Z-167196849087-d539.json`); an ARN with an account; an `amazonaws.com`, `execute-api` or `.elb.` host; an `s3://` URI that is not a `{placeholder}`; a bucket name of this environment (the `scholarchain-course` patterns of `register_bucket_patterns`); an access-key, Anthropic-key or Voyage-key shape. It prints the document, the line and the kind, never the value. It is pattern based because the script makes no AWS call (the value-based `check_no_identifiers` of `run-experiment.sh` and `archive-evidence.sh` needs the account and bucket names from AWS).
- **Write path:** both files are built in the private temporary folder, checked, copied into `OUT_DIR/.incomplete-RC_SHA-XXXXXX/` (`mktemp -d`), validated (`jq empty`, every mandatory field, the Markdown holds the SHA, the tag, every jar checksum and the rule line), checked again, and HEAD must not have moved; only then is the folder renamed to `OUT_DIR/RC_SHA/`. On a failure after the temporary folder exists, no `RC_SHA/` is left and the script prints `INCOMPLETE-FOLDER: PATH`: never commit it; remove it, then run again.
- **Output lines:** `STEP: release-manifest.sh NAME`, `INFO:`, four `SUMMARY: release-manifest ...` lines (counts, `jars_not_present=0`, test counts), `MANIFEST-FOLDER: PATH`, `RESULT: release-manifest.sh ok|failed`.
- **check.sh probes (gate 9):** `--help` (0); no options and an unknown option (2); a missing `--marker` file, a `--clone` folder that is not a Git working tree, a `--clone` repository whose HEAD differs, and a `--clone` working tree at this HEAD without jars (3 each); the fixtures live in check.sh's private temporary folder, and `release-manifest-wrote-nothing` checks that no refusal created the `--out-dir` folder. They run at E4 in the fresh clone, before E10.

## Phase 15 options and loaders (run-bounded-pipeline.sh)

- `--emr-max-units N` (stages hadoop and spark): the EMR managed-scaling maximum of this execution's cluster (execution-input field `cluster.managedScalingMaxUnits`); integer 1..64 in the script, and the state machine fails the execution in its first state, before any cluster, unless `emr_managed_scaling_min_units <= N <= emr_managed_scaling_max_units` (today 2..4). Recorded in `configuration.execution_settings.emr_max_units`.
- `--spark-shuffle-partitions N` (stage spark): `spark.sql.shuffle.partitions` of both Spark steps (field `spark.shufflePartitions`), 8..512, default 32. Recorded in `configuration.execution_settings.spark_shuffle_partitions`.
- `--max-documents N` (loader rag-ingest, optional): passed on as `RagIngestJob --max-documents N` (1..10000000): every run and the retrieval smoke use the first N rendered documents. Recorded in `inputs.loader_options.max_documents` (null = all) and in `inputs.ops_command`.
- `--loader rag-retrieval-eval` (experiment E; `org.scholarchain.rag.eval.RetrievalEvalJob`, no LLM call): `--graph-run-id run:v1:HEX32` (required; passed on as the job's `--graph-run`), `--modes LIST` (optional, comma list without spaces of `graph-only`, `vector-only`, `fused`; fused needs the other two), `--max-seconds N` (optional, 60..3600; job default 1200), `--question-timeout-seconds N` (optional, 5..300; job default 60). The job's `--attempt-id` is the script's own attempt ID, and its `--out` is a new folder inside the task. `--wait-timeout` must be at least the job's total limit plus 300 s (usage error 2 otherwise). Same refusals as every loader: the ops task definition's image tag must be the build commit, and no ops task of the family may be running (one ops task at a time). The report copy goes to `s3://{data-bucket}/rag/retrieval-eval/ATTEMPT_ID/report.json` (put-if-absent); the script prints `EVAL-REPORT: LOCATION` before the task starts and `EVAL-REPORT-COPY: OUTCOME LOCATION` after it, and records `outputs.retrieval_eval_report` (`location`, `copy_outcome`). Container exit 0 means completed with the copy `created` or `already present`; exit 1 (failed, the job's total time limit, or a failed copy) or 2 (refused arguments) makes the stage exit 6.
- Example (E, run by its collector through run-experiment.sh; the values of the signed manifest `experiments/manifests/p15-e-retrieval-modes.json`, `args`): `bash scripts/run-bounded-pipeline.sh --stage load --snapshot dblp-2026-11-01 --loader rag-retrieval-eval --graph-run-id run:v1:f2625d504b12749389cf4f5b1a26aed4 --modes graph-only,vector-only,fused --max-seconds 1200 --question-timeout-seconds 60 --wait-timeout 2400`.
- Sizing `--wait-timeout` (Phase 15 M-03): the pipeline's own rule above (`limit + 300`, `run-bounded-pipeline.sh` around line 683) is a floor, not a safe value. The job checks its total limit only when a question starts, so it can end up to about 12 minutes (720 s) after `--max-seconds` (Phase 15 review finding H-02). The E collector (`experiments/collectors/e-retrieval-modes.sh`) therefore requires at least `limit + 300 + 720` (2220 s at the job default 1200 s) and refuses less with exit 2. Use at least that when you run the loader directly too; the signed manifest uses 2400 (its `notes`, "WAIT LIMITS"). A value between the two rules can end with pipeline exit 7 while the task still works.

## DBLP DTD (Phase 14 decision 7)

The release declares no entities itself and writes non-ASCII characters as DTD named entities (`&eacute;`), so the Hadoop parse needs `dblp.dtd`. Without it the Hadoop stage still SUCCEEDS but rejects every record with a named entity as `undefined_entity`. The driver option `--dblp-dtd PATH` (modules/hadoop, `ScholarChainHadoop`) sets `scholarchain.dblp.dtdPath`; it goes through two `--hadoop-extra-arg` values, in this order: `'--dblp-dtd'`, then `'s3://{data-bucket}/raw/dblp/dblp-2026-11-01/dblp.dtd'`. Do not pass `-D scholarchain.dblp.dtdPath=...` that way: the state machine appends the extra arguments after the application options, and the driver refuses a trailing `-D`. The D6 check: the J01 counter `scholarchain.reject-reason:undefined_entity` is 0. The run record's `configuration.note` and `configuration.extra_args` name the options passed.

## Large uploads (Phase 14 G-07)

D5c's first try sent the 1.1 GB release as one `put-object` and lost it to one dropped connection. `run-bounded-pipeline.sh` (`put_once`, used by `--stage upload-input` and by the ER upload, also `--upload full`) now sends every file above 64 MiB as a multipart upload; files of at most 64 MiB stay one `put-object`. The options and the command lines do not change.

- Never overwrite: a `head-object` check before the start (as before), and `complete-multipart-upload --if-none-match '*'`, which S3 refuses with 412 when the key exists. After a failed complete the script reads the key: this attempt's object (a lost answer) counts as uploaded, the same sha256 from another attempt as `already-present`, other bytes are refused (exit 4).
- Metadata: `scholarchain-sha256`, `scholarchain-commit`, `scholarchain-attempt` are set on `create-multipart-upload`, so later stages read them as before.
- Checksum: `--checksum-algorithm SHA256` on create and on every part. For SHA-256, S3 supports only the composite type on a multipart upload (full-object checksums are CRC only). S3 checks each part; the script also compares each part's `ChecksumSHA256` with its own SHA-256 of the part. `head-object --checksum-mode ENABLED` then shows `ChecksumType` `COMPOSITE` and a `ChecksumSHA256` computed from the part checksums, not from the whole file (the `-N` part-count suffix on that value is unverified); the whole-file sha256 stays in the `scholarchain-sha256` metadata, and the script checks `ContentLength`.
- Per part: 64 MiB read into one temporary file (only one on disk at a time), at most 600 s per try, up to 5 tries; one `POLL: multipart location=... part=I/N bytes=B tries=T` line per part; one `SUMMARY: multipart ...` line per file. A 4.25 GB ER file is 64 parts (68 if it is 4.25 GiB).
- On failure, INT or TERM the script aborts its own incomplete upload (`abort-multipart-upload`, then `list-parts` must show none) and prints `SUMMARY: multipart-abort location=... parts_uploaded=N result=aborted`; the record gets `outputs.multipart_aborted`. This frees the parts of an upload that never became an object; it touches no stored object. A second Ctrl-C during the abort can stop it; the data bucket's lifecycle rule aborts any incomplete upload after one day.
- Record: each `uploaded_keys` entry now also has `method` (`put-object`, `multipart`, or null when the key was already present); a multipart entry adds `parts`, `part_bytes`, `s3_checksum_type`, `s3_checksum_sha256`.
- Needs `dd` and `base64` (both in macOS), and the permissions `s3:AbortMultipartUpload` and `s3:ListMultipartUploadParts` (the human's admin profile has them).
- No resume: a new attempt starts the file again from part 1.

## First runtime-on deploy (D11): rollback policy and desired count

- Rollback: the previous task-definition revisions are the runtime-off placeholders (image tag `placeholder-runtime-disabled`, never pushed), so rollback.sh has nothing good to go back to. On a failure of the first runtime-on deploy, fix forward (a script, code or Terraform repair, then a new package, plan or deploy as the repair needs); never roll back to a placeholder. From the second runtime-on deploy on, the normal policy applies: rollback.sh to the release record's previous revision; anything beyond that goes to the human.
- Desired count (I-28): Terraform ignores `desired_count` after a service exists, so turning the runtime on moves only the scaling targets' minimum of query, evidence and graph from 0 to 1. The Application Auto Scaling API reference (RegisterScalableTarget) says an update of an existing scalable target moves the current capacity into the new bounds, so the count should rise to 1 (untested here). deploy.sh exits 6 and prints every service's desired, running and pending counts when any of the three has desired 0 or running 0 after the wait; no release record is written.
- Remedy if the count stays at 0 (with the human's go): for each of the three services, `aws ecs update-service --cluster CLUSTER --service ROLE --desired-count 1 --query 'service.[serviceName,desiredCount]' --output text` (CLUSTER from `terraform output -raw ecs_cluster_name`). Drift: none in the next plan, because `desired_count` is in `ignore_changes` and 1 is inside the scaling target's bounds (min 1). Then make a new runtime-on plan from the same values (it should show no change), sign it, and run deploy.sh with it to verify the services and write the release record (deploy.sh refuses to re-run a plan it already applied).

## AWS Emulator (Phase 16, decision 12; run book step E14)

Local only: no AWS account, no cost, no network beyond Docker's image build. The emulator is AWS's local emulator of the AWS APIs (https://docs.aws.amazon.com/emulator/latest/userguide/what-is-service.html); on macOS it runs in Docker from an image you build (https://docs.aws.amazon.com/emulator/latest/userguide/getting-started-docker.html). Files: `docker/emulator/Dockerfile` (build-engineer), `config/emulator.json`, `scripts/emulator/env.sh`, `scripts/emulator/setup.sh`, `scripts/emulator/probes.sh`, `scripts/emulator/lib.sh` (shared safety contract), `scripts/emulator/OPERATIONS.md` (which operations are documented, and which stay probes). Status of every emulator script: `static: shellcheck clean`, `human execution required`; the human ran the Phase 16 versions once (E14, `docs/agent-runs/phase-16/runbook-log.md`); the Phase 17 changes to env.sh (the `SCHOLARCHAIN_CFG_*` sweep, step 8 below) and probes.sh (P16-B-03) are `runtime: untested`.

Two terminals: the **emulator terminal** runs only `docker run` (step 5) and shows the emulator's log; the **[EMULATOR] terminal** is every other step after step 8, with the `[EMULATOR] ` prompt. Never use the [EMULATOR] terminal for anything else (its AWS variables point at the emulator), and never run the emulator steps while another sbt process, a source-changing repair or a commit runs. Every line is one zsh line from the repository root.

Rules the scripts and suites enforce (the emulator safety contract, Phase 16 decision 6.6; the scripts' copy is `scripts/emulator/lib.sh`): the endpoint is exactly `https://127.0.0.1:9297` (no `localhost`: with it the Java SDK puts the bucket in the host name, point-sdk-to-emulator.html) and `AWS_ENDPOINT_URL` equals it; `AWS_SHARED_CREDENTIALS_FILE` and `AWS_CONFIG_FILE` are exactly the emulator's files under `$HOME/.aws/emulator/9297/`; `AWS_PROFILE`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_ROLE_ARN`, `AWS_WEB_IDENTITY_TOKEN_FILE`, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` and `AWS_CONTAINER_CREDENTIALS_FULL_URI` are unset; `SCHOLARCHAIN_CONFIG_FILE` and `SCHOLARCHAIN_EMULATOR_RESULTS_DIR` are absolute. The scripts also check the health route and that STS answers with the emulator's single account (compared, never printed or recorded: they print `emulator account confirmed: yes|no`), and pass `--endpoint-url` explicitly on every AWS CLI call. `JAVA_TOOL_OPTIONS` is never set: the sbt `EmulatorTest` configuration gives the emulator trust store to the forked test JVM only.

A re-run, full or partial, starts with a restarted emulator (step 15, then step 5 with the same image), a new run ID and results folder, and `setup.sh` again; setup.sh and probes.sh refuse a results folder that already holds their file.

Environment variables (names): read by the scripts: `SCHOLARCHAIN_EMULATOR_ENDPOINT`, `AWS_ENDPOINT_URL`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`, the eight unset variables above, `SCHOLARCHAIN_CONFIG_FILE`, `SCHOLARCHAIN_EMULATOR_RESULTS_DIR`, `SCHOLARCHAIN_EMULATOR_RUN_ID` (probes.sh, vector key tag), `HOME`, `TMPDIR`; set by env.sh: `AWS_ENDPOINT_URL`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`, `AWS_CA_BUNDLE`, `AWS_EC2_METADATA_DISABLED`, `AWS_DISABLE_HOST_PREFIX_INJECTION`, `AWS_REGION`, `AWS_DEFAULT_REGION`, `SCHOLARCHAIN_EMULATOR_ENDPOINT`, `SCHOLARCHAIN_CONFIG_FILE`; unset by env.sh: the eight variables above, the four ScholarChain API-key variables, every exported `SCHOLARCHAIN_CFG_*` variable (found by name at run time, counted) and every `SCHOLARCHAIN_CFG_*` name ConfigLoader knows.

Exit codes (setup.sh, probes.sh): 0 ok; 2 usage; 3 missing prerequisite (tool, file, results folder, emulator not healthy); 4 refused by a safety rule (one `preflight` line in the results file when the results folder is usable); 5 unexpected command failure; 6 a create or probe call failed (results complete); 7 interrupted.
